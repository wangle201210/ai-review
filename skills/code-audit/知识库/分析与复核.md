# 分析与复核

## 从游戏规则追踪行为

先理解受影响游戏的实际需求、协议和配置，再比较 base/head 的行为。典型链路为“请求/自动动作 → 身份及状态校验 → 扣费 → 定奖 → 奖池及奖励 → 记录/通知 → 恢复”；按该游戏实现核对，不强套另一游戏的顺序或规则。

沿注册包装器、嵌入类型、泛型、回调和实际公共依赖追踪保护。Handler 内没有显式校验不表示没有保护；合法配置被代码误用、内部回调执行错误也可能引发正确性问题。

## 每个候选只需核实五件事

1. **变更归因**：本次改动新增、加重或激活了什么问题？对照旧实现，定位相关 diff。无关历史缺陷不作为 MR finding；全量审计则不要求 MR 归因。
2. **真实触发**：入口已注册、状态和配置条件可能成立吗？区分单测直接调用与生产路径、部署模板与实际部署事实。
3. **正确行为**：依据该游戏需求、协议契约或锁定来源行为，预期的金额、状态、次数或权限是什么？同时检查规则或调控策略本身是否让玩家以不匹配的成本获得奖励；符合原设计不等于没有资金漏洞。需求或可接受的成本边界不明则待补证。
4. **已有防护与恢复**：上层校验、串行调度、幂等、锁、重试、补偿是否已阻断或修复这个场景？重新读取关键证据，主动寻找反例。
5. **具体影响**：发生什么资金、数据、玩法或可用性损害？优先说明运营方资金如何流出、少收或被重复支付，区分确定性损失与待证明的期望收益偏差。是否值得作者修复？危险 API、规则命中和风格偏好本身不构成问题。

安全问题需说明被突破的权限、资源或资金约束。纯业务/可靠性缺陷不必有攻击者，但需要明确违反的契约和错误结果；访问自身资源也可能不当获取运营方资金，不能一概排除。

## 记录与收口

保留真实文件/行号、base/head 行为差异、触发前提、关键调用链、影响和反证即可；不要求固定 ID、底稿文件或模板，交付时将必要证据写入文字回复。依赖证据注明 module@version。源码改变后重新核对位置，不编造代码、测试或日志。

结论分为已确认、已排除、待补证；未检查路径另行说明。关键需求、依赖或部署条件未知不能记作已排除。静态分析和运行证据分别标注，单模型交叉检查不声称独立人工复核。

影响范围仅包含实际核对的路径，不虚构概率或金额。
