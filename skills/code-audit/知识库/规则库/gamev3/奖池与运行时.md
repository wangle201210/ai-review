# G-JP / G-GO / G-LIFE / G-DEPS：奖池与运行时

## G-JP：奖池一致性

定位 `plugins/slots/common/jackpot` 及游戏适配器、配置和 SettleJP 调用。检查：

- gameID、MchID、roomKind 等键字段是否符合奖池共享约定；对象 Copy 是否保留后续必要身份，克隆仅用于纯计算则不要求写库能力。
- Put/HitPot/outDB 中本地与 Redis 更新先后、错误处理、返回奖额与实际扣池是否一致；内部/豁免账号分支是否符合契约。
- 进程 Mutex 保护范围与跨 Pod 锁范围分别是什么；不能把一个 Pod 单游戏误当作只有一个副本，也不能无证据断言多副本正在运行。
- 分布式锁 TTL 是否覆盖临界区；锁所有权、超时续期、释放和原子更新能否防止过期持有者删除后继锁或重复出池。画出可能交错序列，并说明部署前提。
- 重试是否有界/可取消、失败是否误报成功、锁等待是否阻塞房间或关闭；只有真实可达的阻塞路径才确认可靠性缺陷。
- 合法配置下 JP 类型到数组下标的映射、奖励字段和单位是否用对，以及代码取整、实际扣池与返回奖励是否一致。

**证据**：调用者、金额计算、锁与持久化步骤、可能交错、部署条件和实际受影响资产。单个 SetNX 或固定 TTL 本身不是结论。

**验证**：用 fake Redis/已有内存测试设施控制锁到期与写入失败；分别验证同回合重试、两个合法并发操作及错误返回，不连接真实 Redis 或奖池。

## G-GO：Go 边界和资源

核对 map/slice/pointer 的共享所有权、配置发布、协程访问、锁顺序、锁内阻塞、错误路径解锁、context 取消、goroutine/channel 生命周期。数组下标、nil、类型断言和整数转换需要追踪上游不变量，不能看到未检查就报 panic。

确定 Papaya/房间调度是否串行，热更新、通知和后台协程是否绕过该串行约束。对象复制要验证嵌套切片和 map 是否仍别名。静态缺少显式锁也不证明必有并发。

## G-LIFE：构建与生命周期

核实 `BUILD_GAME` 与单 tag、入口 main、GameName/GameID、runner 目录选择、Config/Lobby/Observe 顺序和反向关闭。生产不是动态插件加载，不建议引入 Supervisor、re-exec 或多游戏运行时选择。

核实就绪条件是否覆盖实际需要的配置和牌库初始化，失败能否重试；探针路径和端口依据项目文档和实现。停止/取消时是否有尚未完成的结算或不可中止的等待。部署模板不证明真实网络可达性，Observe 内部路径或明文端口本身不足以确认未授权暴露。

## G-DEPS：版本和调用链

依赖范围和版本定位遵循 [侦察](../../侦察.md)。对范围内的依赖变更，重点核实升级前后相关校验、调度和幂等契约是否变化，以及当前入口是否真正调用这些机制。

依赖缺陷影响到游戏时注明依赖归属和版本，提出修复建议，不擅自修改同级仓库或模块缓存。
