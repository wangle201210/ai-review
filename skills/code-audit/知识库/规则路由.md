# 根据 diff 选择检查项

先读 [规则索引](规则索引.md)，以“变更点 → 行为变化 → 受影响路径 → 检查项”组织审查，不建立默认的逐游戏审批清单。

## 本仓库的实际调用定位

下表是定位提示，不是每个 MR 必须读取的全量清单。以被审查版本的实际符号为准；Ganesha 仅用于说明现有组织方式，其他游戏保留自身差异。

| 改动位置/符号 | 必要的上下文与核查点 |
|---|---|
| `internal/module/cxt/handler.go` | 先找 `room.go` 的 `registerMsg`、`room.Register` 和 `app.HandleStateReq`，再看处理函数。状态校验可能在注册包装器，不能因 Handler 没检查状态就报错。 |
| `RoomContext`、`UserStd`、`UserScatter` | 核对嵌入的 `app.AppContext` 以及 slot-app/game-common 实际版本；本游戏没有方法体不表示校验或扣费不存在。 |
| `UserBonus`、`DoBonus`、`Settle` | 核对 `MoveToNextResult`、`ApplyNextState`、`Bag.NextState/ResetState`，并检查 `OnDisconnectedTimeout` 的自动推进路径是否同样受本次变化影响。 |
| `game_cache.go`、`ExtBag` | 对照 `NewGameCache` 的保存字段与 `RestoreGameCache`、嵌入缓存恢复过程；只针对本次新增或改变的数据确认恢复契约。 |
| `internal/module/jackpot`、`common/jackpot` | 对照游戏适配器、`GetJackpot` 的 gameID/MchID/roomKind、`Put/HitPot` 与 `SettleJP`；固定奖励、累计奖池、记录和实际入账分别追踪。 |
| `conf`、`cacheConf`、`InitCacheConf` | 对照商户/配置组、`conf.NewCacheConf`、`common/configset` 和运行时消费；不能只验证配置解析成功。 |
| `misc/hot`、`common/panelcache`、`common/lifecycle` | 检查 `Initialize/Load/Save/Ready`、`InitHot` 和 `IsGameReady` 的发布顺序与失败路径，不将共享牌库按商户重复初始化作为默认正确行为。 |
| `common/feature`、`cardlib`、`bonus`、`panel`、`playconf` | 只核查变更函数的真实调用者、游戏参数、数值单位和玩法前提；公共实现不代表所有游戏都接入或规则都相同。 |
| `cmd/gamev3`、`plugin.go`、`internal/runner` | 核对单 tag/main、conf/g 身份、Papaya 模块顺序和仅按 panelDB 存在选择工作目录；进程级 init 在单游戏产物中可为合法设计。 |

共享 STD/SCATTER 协议还可能来自 game-common 的 `modules/room/slotnew/proto`；只读取游戏本地 pb 会漏掉实际请求定义。游戏自己的 pb 是正式协议来源之一，不因模拟器也引用它就排除。

按实际语义补充定位，仅加载与变更有关的规则；规则文件中的所有检查均沿用入口范围，不要求逐项全跑。
